# CX-02 — Perfis e vínculo paciente–fisioterapeuta

## Entrega

Implementação na branch `feature/cx02-patient-professional`, criada a partir de `origin/develop`. A árvore estava limpa ao iniciar. O código de interface e os pipelines anteriores foram mantidos na linha de desenvolvimento correspondente.

| Tela | Funcionalidades |
| --- | --- |
| `/patient/profile` | Nome editável, identificação real da conta, e-mail e papel para consulta, validação e feedback de gravação. |
| `/professional/profile` | Nome, regional e número CREFITO obrigatórios, código do perfil para vínculo, Contas legadas com CREFITO nulo podem completar o cadastro. |
| `/patient/physiotherapist` | Estado vazio, solicitação por código profissional, solicitações pendentes, cancelamento, vínculo ativo, confirmação de encerramento e histórico de recusas/cancelamentos/encerramentos. |
| `/professional/patients` | Solicitações recebidas, aceite, recusa, pacientes ativos com paginação e encerramento de vínculo. |
| `/professional/patients/[patientId]` | Identificação básica autorizada, consultada novamente no backend. |

Os dashboards oferecem links para perfil e acompanhamento. O cadastro existente ganhou os campos CREFITO exigidos pelo contrato profissional, preservando a composição visual da autenticação.

## Contratos utilizados

A fonte é o backend disponível em `../ctrl-x-backend`, principalmente `app/api/v1/endpoints/care.py`, `app/schemas/care.py`, `app/schemas/professional.py`, `app/services/care.py`, `app/models/professional_link.py` e `app/schemas/auth.py`. Os arquivos de documentação do backend foram conferidos com a implementação.

Todas as rotas usam o prefixo `/api/v1`.

| Método | Endpoint | Uso |
| --- | --- | --- |
| GET | `/auth/me` | Identidade e papel da sessão CX-01. |
| GET | `/me` | Perfil próprio e CREFITO informado. |
| PATCH | `/me` | Nome e, para fisioterapeutas, regional/número CREFITO. Campos imutáveis e status são excluídos do payload. CREFITO sem alterações é omitido. |
| GET | `/me/professional-links?limit=20&cursor=…` | Todos os vínculos do usuário, seguindo os cursores até o fim. |
| POST | `/me/professional-links` | Solicitação com `professional_id` do perfil. |
| POST | `/me/professional-links/{id}/accept` | Aceite com retorno do vínculo ativo. |
| POST | `/me/professional-links/{id}/reject` | Recusa, HTTP 204. |
| POST | `/me/professional-links/{id}/revoke` | Cancelamento de pendente ou encerramento de ativo, HTTP 204. |
| GET | `/patients?limit=20&cursor=…` | Pacientes ativos autorizados, com botão para carregar a próxima página. |
| GET | `/patients/{id}` | Identificação de paciente autorizado. |

O cadastro CX-01 continua em `POST /auth/register`, com CREFITO adicionado apenas ao payload profissional. `id` do perfil e `user_id` da conta são distintos e conferidos. O cliente usa `fetchJson`, cookies `credentials: include` e `cache: no-store`.

## Estados e privacidade

Os estados `pending`, `active`, `rejected`, `cancelled` e `revoked` vêm da API. O aceite é apresentado como solicitação aceita e vínculo ativo. Históricos legados `revoked` continuam aparecendo como encerrados conforme o contrato, sem inferência de intenção.

O paciente só vê o formulário de nova solicitação após ler todas as páginas e confirmar ausência de vínculo ativo. Respostas inconsistentes com dois ativos para um paciente interrompem a apresentação. O backend decide conflitos concorrentes. Cada mutação aguarda a resposta e atualiza as consultas, sem alterações otimistas de estado. Conflitos 409 provocam nova leitura.

O encerramento ativo usa um diálogo HTML nativo com foco inicial no cancelamento, Escape e retorno do foco. Após uma ação, as consultas de pacientes e identificações anteriores são canceladas e retiradas do cache em memória antes da atualização. Erros 401 ocultam a área, limpam consultas sensíveis e oferecem novo login. Erros 403/404 ocultam dados da consulta que perdeu acesso. Dados são revalidados ao retornar à janela e vínculos/identificações são consultados a cada 30 segundos enquanto a tela está montada. A autorização de cada requisição continua no backend.

Falhas de gravação mantêm o formulário preenchido. Falhas de rede em atualização de perfil em segundo plano mantêm o editor e apresentam recuperação. E-mail, papel, IDs e CREFITO aparecem para consulta. Nenhum token ou registro é persistido no armazenamento do navegador.

## Limitações confirmadas

- A API não oferece diretório público nem leitura de perfil de fisioterapeuta pelo paciente. A identificação disponível é o UUID compartilhado pelo profissional. Nome e CREFITO de terceiros aguardam um contrato de leitura autorizado.
- Solicitações pendentes disponibilizam o código do paciente. O profissional confirma esse código com o solicitante. O nome é obtido somente após autorização pela listagem de pacientes ativos.
- O CREFITO é declarado e passa por validação de formato. Dados de pacientes exigem vínculo ativo.
- Os endpoints de CX-02 existem nos arquivos locais. A disponibilidade da mesma versão nos ambientes remotos depende da publicação do backend e das migrations correspondentes, incluindo `0005_professional_crefito` e `0006_link_decisions`.
- A validação de formato CREFITO no formulário segue o schema local.

## Como testar localmente

1. Use Node 22 atualizado e execute `npm ci`.
2. Configure `NEXT_PUBLIC_API_URL=http://localhost:8000/api/v1` em `.env.local` para o backend de desenvolvimento. Preserve as outras configurações locais. Confirme a origem do frontend em `CORS_ORIGINS` e as migrations no banco de desenvolvimento.
3. Execute `npm run dev` e autentique-se com contas sintéticas de paciente e fisioterapeuta. Acesse as novas telas pelos links do dashboard.
4. Altere o nome do paciente e recarregue para conferir persistência. Simule falha de rede ao salvar e confira que o texto permanece disponível.
5. Complete o perfil profissional com regional/número. Teste a recusa e o encerramento de vínculos de teste existentes, quando houver.
6. Solicite e aceite um vínculo com as contas sintéticas. Confira a lista de pacientes e se o acesso termina após a revogação.
7. Execute `npm run lint`, `npm run typecheck`, `npm test` e `npm run build`.
